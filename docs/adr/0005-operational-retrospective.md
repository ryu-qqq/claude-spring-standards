# ADR-0005: 운영 회고 — "AI 100% 컨벤션 준수" 의 한계와 잔존 가치

- Status: Accepted (회고 기록)
- Date: 2026-05-26

## 컨텍스트

conventionHub 의 처음 목표는 명확했다 — **"기술스택이 같은 프로젝트가 컨벤션을 단일 원천 (DB) 으로 공유 + AI 가 MCP 로 조회해서 100% 준수"**.

직접 만들어서 본인의 다른 프로젝트들에 적용해보고 운영해봤다. 이 ADR 은 그 운영의 솔직한 회고.

[README 의 운영 회고](../../README.md#-운영-회고) 가 짧은 요약이고, 이 ADR 은 그걸 더 깊게 풀고 시도한 우회들의 결과까지 기록.

## 잘 동작한 것

먼저 잘 동작한 것부터.

- **컨벤션 단일 원천 (DB + REST API)** — Spring API 가 안정적으로 컨벤션 CRUD + 조회 서비스. Flyway 마이그레이션으로 컨벤션 변경 이력도 관리됨
- **MCP 인터페이스** — FastMCP (Python) 가 Claude Code, Cursor 등 여러 AI 도구에서 같은 컨벤션을 동일하게 조회 가능
- **`suggest_convention` 의 3가지 전략** — `code_prefix`, `applies_to_layer`, `description_keywords` 의 조합으로 신규 규칙 등록 시 적절한 convention 그룹 추천. 등록 작업의 인지 부담 감소
- **CodeRabbit 자동 PR review** — 컨벤션의 일부가 PR 시 자동 review 로 짚어져서 사람 리뷰어 부담을 덜었음

## 잘 안 된 것: "AI 가 100% 준수" 라는 목표

세 가지 메커니즘적 벽을 만났다. 일반론적 변동 (LLM 도구 다양성, 모델 업데이트) 도 영향을 주지만, 더 본질적인 건 아래 세 가지.

### 벽 1 — 메모리에 있는데 적용을 못 한다

**증상**

컨벤션을 MCP 로 조회해서 LLM 컨텍스트에 잘 넣어도, 코드 생성 시 그걸 일관되게 따르지 못하는 경우가 많았다. 컨벤션이 "참고 자료" 로는 인식되는데 코드 생성의 **직접적 제약** 으로 작동하지 않는 느낌이 들었다.

예: `BLOCKER` severity 의 "Lombok 금지" 가 컨텍스트에 있는데도 LLM 이 `@Builder` 가 포함된 코드를 생성하는 케이스가 종종 발생.

**시도한 우회**

- 컨벤션 텍스트를 더 강한 톤으로 작성 ("절대 금지", "MUST NOT") → 효과 제한적
- BLOCKER severity 를 별도 섹션으로 강조 → 일부 개선되지만 100% 보장 X
- detection_pattern (regex) 을 함께 제공 → AI 가 직접 검증하지 않으면 무의미

**왜 우회가 본질 해결이 아닌가**

Instruction following 자체가 LLM 의 확률적 동작이라 컨벤션을 "보장" 할 수 없다. 시스템 프롬프트 / 사용자 메시지 / 컨텍스트 어디에 넣든 100% 제약이 아닌 강한 가이드일 뿐.

### 벽 2 — 컨벤션 로딩 자체가 컨텍스트 비용

**증상**

162개 규칙을 다 컨텍스트에 넣으면 그 자체가 context window 의 상당 부분을 차지한다. 결과적으로 정작 코드 생성에 쓸 컨텍스트 (사용자 요구사항, 기존 코드, 도메인 지식) 가 줄어든다.

**시도한 우회**

1. **`list_rules` 경량 인덱스** — code/name/severity 만 가져오는 light query. 필요한 규칙은 `get_rule` 로 lazy 조회
2. **Serena Memory 캐싱** — `/sc:load` 시 인덱스를 Serena Memory 에 쓰고 개발 중 read 로 재사용
3. **레이어별 필터링** — `layers=["DOMAIN"]` 같이 작업 중인 레이어만 조회

**결과**

세 우회 다 컨텍스트 비용 자체는 줄였다. 하지만 본질적 트레이드오프는 그대로:

- 인덱스만 보면 LLM 이 어떤 규칙이 적용되어야 할지 판단 못 함 → 결국 `get_rule` 호출 필요 → 컨텍스트로 들어감
- Lazy 조회를 LLM 이 적절한 시점에 한다는 보장이 없음 (벽 1 의 instruction following 한계가 여기서도 반복)
- 필터링은 "어떤 레이어가 관련 있는지" 를 LLM 이 판단해야 하는데 그 판단 자체가 정확하지 않음

본질적으로 "컨벤션이 코드 생성의 직접 제약이 되려면 컨텍스트에 있어야 한다" 와 "컨텍스트는 유한하다" 가 충돌. 이 트레이드오프를 우회하는 깔끔한 답이 안 보였다.

### 벽 3 — LLM 메커니즘이 black box 라 시스템적 개선이 어렵다

**증상**

왜 어떤 컨벤션은 잘 따르고 어떤 건 안 따르는지 패턴이 잡히지 않았다.

- Severity 별 실험 (BLOCKER vs MAJOR) → 일관된 결론 안 나옴
- 규칙 길이 별 (짧은 한 줄 vs 긴 설명) → 결론 안 나옴
- GOOD/BAD 예시 유무 → 일부 케이스에서 도움되지만 일반화 어려움
- 규칙을 시스템 프롬프트에 vs 메시지에 → 모델/도구마다 다름

**왜 시스템적 개선이 어려운가**

Attention 메커니즘이나 instruction following 의 정확한 동작이 black box 라 **"이렇게 바꾸면 더 잘 따른다" 의 가설을 검증할 수 있는 방법이 없다.** 실험해도 N=1 의 결과지 일반화 못 함.

게다가 같은 LLM 도 모델 업데이트마다 동작이 미묘하게 바뀌므로, 한 시점의 최적화가 다음 모델에서도 유효하다는 보장이 없다.

## 그래서 무엇이 남았나

### 발상 자체는 여전히 옳다

**기술스택이 같은 프로젝트가 컨벤션을 단일 원천으로 관리한다** 는 명제는 LLM 의 100% 준수와 무관하게 살아있다. 컨벤션이 흩어져 있으면:

- 같은 패턴이 프로젝트마다 다르게 적용
- 새 프로젝트 시작 시 컨벤션 재정의 비용
- 컨벤션 업데이트가 일부 프로젝트에만 반영되는 동기화 문제

단일 원천 + MCP 조회 인터페이스는 이 문제들의 인프라적 해결책으로 유효.

### 보조 도구로는 충분히 유용했다

"AI 가 100% 준수" 가 안 되더라도, 다음 조합은 사람 리뷰어의 부담을 명확히 줄였다:

- **MCP 조회** — AI 가 적어도 컨벤션을 한 번은 인지함. 100% 는 아니지만 baseline 보다는 개선
- **`suggest_convention`** — 신규 규칙 등록 시 분류/매핑 자동화. Human 결정 시간 단축
- **CodeRabbit PR 자동 review** — 컨벤션의 일부가 PR 단계에서 자동 짚힘
- **`docs/coding_convention/` 146 문서** — 사람 리뷰어가 PR review 시 참고할 명시적 기준

이 조합이 "100% 보장" 은 아니어도 "리뷰어 부담 감소" 라는 더 현실적 목표는 달성.

### "이 분야는 아직 정답이 없다"

이게 가장 정직한 인식이다. LLM 의 instruction following / 도구 활용 / 컨텍스트 효율 같은 분야는 **아직 누구도 권위자가 아니고 best practice 도 형성 중**.

- OpenAI / Anthropic 모두 "LLM 에 가이드를 어떻게 주는가" 의 명확한 표준 없음
- Cursor / Claude Code / Copilot 등 도구마다 컨벤션 활용 방식이 다르고 업데이트마다 바뀜
- MCP 자체도 신생 프로토콜이라 "어떻게 써야 효과적인가" 의 사례가 쌓이는 중

그래서 conventionHub 가 "AI 100% 준수" 에 성공하지 못한 것은 **이 분야의 현재 단계 그 자체** 이지 시스템 설계의 결함이라고 단정하기 어렵다. 동시에 "잘 됐다" 고 주장할 근거도 없다 — 그저 시도해본 한 사례.

### 다음 단계에 의미가 있을 수 있는 것

LLM / MCP 생태계가 진화하면 conventionHub 의 발상이 더 유효해질 가능성 있는 지점:

- **MCP 도구 호출의 정형화** — LLM 이 "코드 생성 전에 반드시 MCP 조회" 같은 패턴을 표준으로 따르게 되면 벽 1 일부 해소
- **컨벤션의 컨텍스트 효율적 표현** — 162개 규칙을 작은 토큰으로 표현하는 압축 방식 (예: 규칙 ID + LLM 이 학습한 표준 매핑) 이 나오면 벽 2 해소
- **Instruction following 의 정형화** — 모델 학습 단계에서 "이런 가이드는 반드시 지킨다" 같은 강제 메커니즘 (constraint-based decoding 등) 이 나오면 벽 1 본질 해소

이 중 어느 것도 지금은 없다. 그래서 conventionHub 의 현재 모습은 "이 가능성을 미리 시도해본 것" 으로 위치 짓는다.

## Consequences

### 좋은 점

- 직접 만들어서 운영해본 결과 LLM / MCP / Convention enforcement 의 본질적 한계와 우회의 가능성을 코드로 학습
- 단일 원천 + MCP 인프라 자체는 안정적 자산
- 보조 도구로서의 유용성은 실측으로 확인

### 나쁜 점

- 처음 목표 (AI 100% 준수) 는 달성 못 함
- 운영 부담 (Spring + Python + AWS Lambda + 컨벤션 데이터 관리) 은 보조 도구로 쓰기엔 큰 비용
- "100% 준수 안 됐다" 의 책임이 시스템에 있는지 LLM 에 있는지 black box 라 시스템적 개선 방향이 안 잡힘

### 리스크

- 이 분야가 LLM 진화에 따라 빠르게 바뀌므로 conventionHub 의 현재 설계가 6개월 뒤에도 유효할지 불확실
- "AI 컨벤션 강제" 라는 카테고리 자체가 다른 도구 (Cursor Rules, Claude.md, OpenAI Custom Instructions 등) 와 fragmented 되어 있어서 표준 합의가 멀어 보임

### 대안

- **Cursor Rules / Claude.md / Copilot Custom Instructions** — 로컬 파일 기반의 가벼운 대안. 단일 원천 X 지만 구축/운영 부담도 X
- **컨벤션 코드 자체로 표현** (예: ArchUnit 테스트, Checkstyle/PMD 룰) — LLM 에 의존하지 않고 정적 분석으로 강제. 100% 준수는 가능하지만 표현력 제한
- **수동 review + 체크리스트** — 시스템 없이 사람 리뷰어가 docs/coding_convention/ 146 문서를 기준으로 review
